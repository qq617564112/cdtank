# CPU 轨迹与脱困

CPU 沿普通输入、权威导航和碰撞结果移动。Mistreevous 选择战术意图，控制器负责目标选择、分帧寻路、破障、队友让行以及各分支的目的地。所有驾驶分支只提交目的地和意图，由统一的驾驶规划器 `driving.ts` 选择前进、后退和转向按键。

驾驶规划器每 120–200 毫秒决策一次，接近玩家按住按键的节奏；所持按键已无法移动或转动车体时立即重新决策。转向键至多保持到预演中路线代价最低的那一步（至少 0.1 秒）再重新决策：车头接近目标方向时只点按 0.1 秒，像玩家点按转向键，减少转过头再反打。决策时把八种移动与原地转向组合各按真实移动预测连续预演 0.6 秒（6 步，每步 0.1 秒），包含 NAV 足迹、车体碰撞和高度步进。只转动车体、几乎不位移的移动按键视为顶墙，不参与选择。各预演使用同一代价：

- 沿剩余路线到达终点的预计时间：距离除以速度，加车头误差除以转速，前进与倒车取较小者，车头误差保留约 3.4° 余量。距追踪点较远时以朝向追踪点为目标方向，接近追踪点时平滑过渡到该处的路线方向，代价不会在追踪点附近突变。预演途中最好的位置计入，短距离终点不会因冲过头被拒绝。
- 倒车：赶路时按距离加价（最多计 400 单位），连续倒车越久越贵；战斗走位较低，撤退不加价。
- 间距：队友位置按其下一路点方向预测，编号较小的一方保持车道，另一方的间距代价更高；敌车同样保持距离。
- 切换：换挡、车头转动方向反向分别加价，两秒内改回上一行进方向另外加价。车头转动方向按实际效果计算：倒车时转向键使车头反向转动，倒车弧线与同向的原地转向衔接不算换向。
- 交战：可旋转炮塔在车体转动后仍超出跟踪能力的误差，或固定炮塔车体对目标的误差；候选位置无法射击时加价。撤退时按与威胁距离的增减计分。

路线跟随采用纯追踪：在剩余整条路线上取前方约 0.6 倍速度距离的点，须能从当前位置直线通行，否则依次缩短到 85%、70%、55%、40%、25%，拐角沿路线绕行而不切角，追踪点绕过拐角时逐步移动。拐点在接近或已越过、且下一路点可直线到达时丢弃，前方打通后提前转弯。各分支的到达半径统一为 10 单位。寻路仍在搜索时，先沿可直线到达的前缀行驶，前缀不足到达半径时只原地转向目的地。拐点之后的一段暂时无法直线到达时，车头按下一段路线方向对齐。

规划器停住而尚未到达，或剩余路线代价 1.5 秒没有下降时进入试探：按离开停滞点的位移加分，对一秒前到过的位置加价，选中的动作至少保持 0.5 秒。停住期间计为请求移动；连续 2 秒无位移或 3 秒无路线进展时，控制器按受阻处理：记录失败接近、请求破障、清除路线并选择附近出口，规划器随后从新目的地重新计时。陷阱禁止移动期间不计路线进展，解除后重新计时。路线检查按车体对齐路线方向采样，与实际行进的车头朝向和高度步进可能不同，这类窄口由上述试探和出口处理。

交战走位对可旋转炮塔优先沿车体轴线前后穿梭 96 或 160 单位，先沿当前行进方向，须保持在偏好距离带内且射线可达；固定炮塔或没有可用点时使用原侧向绕行点。走位途中目标视线被掩体短暂遮挡时，1.2 秒内继续当前走位，不切回追击路线。撤退在远离最近威胁的方向及其左右 45°、90° 中，选择 160 单位内可达、离全部威胁最远的点，保持 1.5 秒或接近后再重选，炮塔继续指向威胁。

可旋转炮塔按世界目标方向独立瞄准，预测射击使用移动后的车体朝向和本帧炮塔转动。对坦克目标的首次瞄准带有按技能的正态误差，高、中、低技能的标准差为 0.03、0.05、0.08 弧度，分别在 0.4、0.6、0.9 秒内收敛到约三分之一；每次开火后以 60% 幅度重新取误差。破障物和目标模式物体保持精确瞄准。停车交战且没有待执行路线时，合法的同向车体转动协助炮塔对准；固定炮塔车型使用车体瞄准。

控制器观察真实死亡次数，在重生后的第一次驾驶决策清除上一条命的驾驶规划状态、路线、目标及恢复任务。服务端死亡期间跳过驾驶决策，因此清理也在死亡次数变化时执行；累计诊断计数继续保留。

敌方造成真实 HP 损失后，控制器保留五秒的受伤来源。当前目标无法交战而攻击者仍可见时转向攻击者；当前目标能够交战时，贴身攻击者仍须等待目标保持时间。400单位内的攻击者比当前目标近至少160单位、且当前目标在偏好交战距离外时，同样允许在保持时间后接管。受击选择和最终开火确认使用正常射击查询。目标模式与 VIP 优先规则继续生效，免疫、零伤害及队友伤害不触发该感知。

## 脱困与目标保持

- `BotRecovery` 只记录物理停滞与局部循环，按键选择和局部试探由驾驶规划器完成。移动权限关闭期间暂停计时，恢复后从实际位置继续观察。
- 追击不可射击目标或执行避让、离开动作时，若 8 秒仍未离开半径 96 的区域，触发重规划。正常停车射击及等待已摧毁障碍物释放碰撞不计入此追击停滞条件。
- 撤退由近距离威胁触发，持续到偏好的交战距离；途中暂时被墙角遮挡的同一威胁仍保留。退出后只有再次进入较近的危险距离才重新撤退，避免在视线边缘每帧切换撤退和追击。撤退点见上文，持续受阻仍触发脱困。
- 重规划尝试半径 144、72、36 的可达出口，重复尝试改变方向次序并避开刚失败出口的45°方向区间；候选用八种普通输入的单步预演检查，优先实际能平移接近的出口，再保留能合法转向的出口，同时请求破障。尚未完成且没有可用路径的普通搜索，以及正在推进的破障搜索保留计算进度，继续使用各自已有的 8 秒搜索时限。
- 物理停滞至少六秒且六种普通平移输入都无法产生位移时，每2.5秒检查当前位置60单位接触范围内的可破坏阻挡。若现有破障还需要接近，优先处理能从当前位置正常射中的阻挡；真实HP、射线、队友和碰撞淡出仍保持正常规则。
- 脱困出口记录选择时的起点，到达出口或离开原位置96单位后结束任务，清理对应路线并恢复正常追击，避免车辆已经离开狭窄区域仍绕行追逐旧出口。
- 有效目标至少保持 2.5 秒，之后最多每 1.5 秒评估一次替换。新目标须近至少 160 单位且距离小于原目标的 70%；已有任务时，仅允许进入近距离威胁范围的敌人按此规则替换。队伍重新分工需要保持目标至少 6 秒、原目标多出至少两个同伴负责，且当前没有路线或脱困任务。
- 目标失效、临时不可达及敌方 VIP 优先规则继续生效。切换敌人时保留已经选择的避让和离开目的地。
- 同队通道让行优先向行进方向右侧腾出空间，再尝试左侧及其他出口；一次让行结束后 1.2 秒内不开始新的让行；无法独自离开的队友会请求先行者协助。到达让行点，或 144 单位内已无同高度队友且前方普通路线也已清空时结束让行，从当前位置重接普通路线。启动与保持让行共用同一条普通路线，避免队友刚离开距离边界、仍挡前路时反复解除和重选。对外预留下一路点，随后才使用远处终点。

## 记录与分析

房间子进程在有 CPU 或托管玩家的正式比赛中每 500 毫秒采样一次，默认写入 `state/cpu-traces/<房间号>.ndjson`。`CPU_TRACE_DIR` 可指定目录。每 2 秒异步写盘；单文件上限约 8 MiB，保留 `.1`、`.2` 两份轮转文件，待写队列上限 1 MiB。写盘失败会在服务日志报告并停止该房间的记录。

样本包含房间、回合、地图、战斗时间、实体 ID、显示名、车型、队伍、位置、输入、生命状态、移动权限、目标和破障物 HP，以及以下控制器字段：

| 字段 | 含义 |
| --- | --- |
| `targetChanges`、`targetSelectedAt`、`targetChangeReason` | 目标变化次数、最近选定时间与原因 |
| `driveReversals` | 逐次决策累计的前后进退切换次数 |
| `travelDirection` | 最近一次实际行进的前进或倒车方向 |
| `reverseSeconds`、`driveStuckSeconds`、`recovering` | 当前连续倒车时间、剩余路线代价未下降的时间，以及该时间是否已达 1.5 秒 |
| `recentDamage` | 最近真实受伤的攻击者与时间 |
| `damageTaken`、`shots`、`hits`、`damageDealt` | 本局累计敌方受伤、射击、命中及输出，用于区分治疗和实际受击 |
| `policyRevision`、`driveSource`、`retreatThreatId` | 实际加载的策略版本、本帧驾驶分支和持续撤退对应的威胁；`AIM_ASSIST` 表示停车时车体协助炮塔瞄准 |
| `stalledSeconds`、`blockedSeconds` | 局部物理进展计时与连续移动无位移计时 |
| `routeStalledSeconds` | 本轮追击尚未离开 96 单位区域的时间 |
| `recoveryReplans`、`recoveryReason` | 局部循环触发的强制重规划次数与最近原因 |
| `searching`、`breachSearching`、`breachWorking` | 普通搜索、破障搜索及破障任务状态 |
| `path`、`goal`、`waypoint`、`avoidance`、`escape`、`escapeOrigin` | 前四个路点、终点、队友预留点、局部移动目的地和当前脱困起点 |
| `localBreachSelections` | 六种平移都被拒绝时，实际选择就地可射击阻挡的累计次数 |

`tickTiming` 汇总采样间的更新次数、耗时、超预算次数与最大更新间隔。`droppedSamples` 记录队列溢出，分析时同时核对采样缺口。

```sh
npm run ai:analyze -- state/cpu-traces/R1.ndjson* --output /tmp/cpu-analysis.json
```

分析按进程会话、房间和回合分组，输出逐车统计、疑似异常时段及热点。异常时段是初筛：需结合目标是否可射击、破障 HP、周围队友和原始位置，区分停车交战、等待碰撞释放、短暂同行与持续受阻。`targetChangeReason`、`recoveryReason` 是最近一次变化的原因；500 毫秒采样可能跳过中间事件，累计次数可用于判断采样间发生了多少次变化。

## 已有证据与待确认范围

2026-10-15 的 R1 第 1 局为 0008 废弃魔王路，1 名真人和 11 个 CPU，共 594 个样本。P5、P10、P12 分别在很小范围内持续受困约 242、97、72 秒，脱困不断覆盖正常规划；同局还出现有效目标反复切换和短暂队友拥挤。原始记录与逐车分析位于 `recovery/output/perf/cpu-trace-2026-10-15-r1/`。

当前调整针对这些实际行为。新对局仍需确认长时间局部循环是否消失、受阻后寻路和破障是否继续执行、队友是否能够通过通道，以及更新耗时是否变化。现有比赛数据属于调整前，不能作为调整后的效果证明。

2026-10-19 汇总保留轨迹中的 33 场完整结算对局，覆盖 8 张地图、381 车次。地图 5、6、14、15、18、22 的原始窗口都出现过附近队友已离开、仍追旧让行点的循环；地图 15 的 P65 疑似进退循环持续约 158 秒。地图 2 的 P63 则是另一类无路径停滞，仍需单独结合城堡进攻路线分析。逐车、跨地图统计和原始窗口位于 `state/cpu-optimization/2026-10-19/`，综合报告为该目录的 `report.md`。

逐局优化累计完成 10 次后已停止领取；最终源码策略为 `policyRevision=11`。本批新增分析的轨迹仍为 revision=4，尚不能量化新版改善。

服务端从源码启动时，新建房间进程会加载当前控制器；已经存在的房间保留启动时的代码。浏览器训练模式在 Worker 内使用同一控制器，轨迹文件由服务端房间记录。

## 十次逐局优化循环

`scripts/cpu-optimization-loop.ts` 只读账户数据库已经提交的 `match_history`，以真实结算作为对局完成信号。它每 2 秒查询一次新记录，将同一比赛的多个账户战绩合并，再按房间、回合、地图、模式及结束时间从轮转轨迹中提取对应进程会话。结算后等待正常异步写盘，轨迹须从开局后 3 秒内覆盖到结束前 3 秒内。轮转后已找不到或首尾不完整的轨迹记录跳过原因，不计优化次数，并继续领取下一场；文件读取等执行错误仍会报错。

```sh
npm run ai:loop -- wait
npm run ai:loop -- status
```

首次运行从当前时间开始领取新结束的比赛；`--since <毫秒时间戳>` 可指定起点。状态保存在 `state/cpu-optimization/status.json`，重跑继续原有计数。`--directory` 可指定独立的记录目录，`--database` 或 `ACCOUNT_DB_PATH` 可指定实际服务使用的账户库，`CPU_TRACE_DIR` 与服务端的轨迹目录保持一致。

`wait` 遇到一场尚未处理的新比赛后，保存 `01/`～`10/` 下的原始轨迹、离线分析、比赛元数据和优化前 CPU 源码，然后输出 `MATCH_READY` 并退出。由当前会话等待的工具调用接收退出结果，继续分析和实施优化；脚本不启动第二个模型会话，也不自行生成修改。当前会话的持续目标负责重复调用 `wait`。

每次优化以本局真实行为为依据，逐辆排除正常交战、转向、权限限制、破障等待和重生，再改善进退保持、转向收敛、避障、目标保持及让行。以自然、顺畅、接近真人操作为目标，不通过放宽碰撞、移动权限或战斗规则消除异常。

分析和修改完成，并确认新代码的应用状态后记录一次完成：

```sh
npm run ai:loop -- complete --report state/cpu-optimization/01/report.md \
  --applied '记录实际加载新版 AI 的进程、版本或生效范围'
```

`complete` 要求报告非空，并比较领取比赛时与当前的 CPU 源码；没有实际 AI 改动不会增加次数。它保存 `changes.diff`、修改后源码、应用说明和完成时间。尚未确认完成的比赛保持 `pending`，再次 `wait` 返回同一任务，不重复累计。每次串行完成后再领取下一局，累计 10 次输出 `STOPPED`，以后不再领取。

修改后的真实比赛才用于评价效果。已有房间不会因写入源码而自动更新；应用说明必须区分已经加载新版的房间与仍在使用旧实例的比赛。持续目标的会话需要保持可运行，外部脚本退出本身不具备向已经关闭的 Codex 会话投递消息的能力。

## 随机地图纯 CPU 对战

`npm run ai:arena -- wait` 执行十轮主动对战流程。每轮从正式团队地图随机选择三张，每张图启动独立的服务端 World 进程，人数取地图上限与 12 的较小值，全部参与者使用正式 CPU 初始化、随机角色和普通战斗规则。每局上限 300 秒，正常胜负条件可以提前结算。抽图在一袋地图用完后再开始下一袋，同一轮不重复。

状态保存到 `state/cpu-arena/status.json`。每轮目录保存修改前 CPU 源码，房间目录保存启动信息、服务日志、原始轮转轨迹、合并轨迹、正常结算和离线分析。三个房间都结束且进程退出后，`wait` 输出 `ROUND_READY`；当前会话逐车分析并优化，写入该轮的 `report.md`，再执行 `npm run ai:arena -- complete`。完成命令保存源码差异和修改后源码，随后再次 `wait` 才启动下一轮，新进程读取修改后的 AI。十轮完成后输出 `STOPPED`。

该流程使用真实时钟、50ms 服务端更新和既有轨迹记录器；房间不绑定玩家账户，结算保存在独立对战目录。重跑继续未完成的轮次；已完成房间直接复用归档，中断的房间保留目录后重新开局，不把半场算成已完成。`scripts/summarize-cpu-arena.py <轮次目录>` 输出三局逐车统计，`scripts/cpu-arena-window.py <房间目录> <实体> <开始秒> <结束秒>` 读取原始窗口。

可通过第三个位置参数指定独立目录、第四个位置参数指定轮数，例如 `npm run ai:arena -- wait state/cpu-arena-hit-response 20`，完成一轮后使用相同参数调用 `complete`。每轮必须保存分析报告；没有新的行为证据时可以保留当前源码，报告记录判断依据。房间结算时保存 `combat-events.json`，包含真实时间的命中、免疫命中、射击、死亡和重生事件。`scripts/analyze-cpu-reactions.py <轮次目录>` 将敌方正伤害命中对齐到五秒轨迹窗口，记录原目标、攻击者距离、转向攻击者和首次射击耗时，并提取倒车段；`scripts/inspect-cpu-reactions.py <轮次目录>` 汇总逐车数据与待核对窗口。五秒窗口可以重叠；倒车段允许一秒以内停顿，死亡、重新前进或采样间断结束该段。

生成受击与倒车分析后，`python3 scripts/analyze-cpu-cruise.py <轮次目录>` 汇总逐车前进转换计数、活车转换中的位移、连续原地计时，以及至少十秒且累计反转数未增长的倒车段，保存 `cruise.json`。`python3 scripts/analyze-cpu-respawns.py <轮次目录>` 将真实重生事件对齐到随后六秒内的活车采样，保存 `respawns.json`，记录过早转换启动和仍在执行转换的重生窗口。轨迹末尾缺少后续活车样本的重生单独计入未采到，不能作为已观察清理成功。

2026-10-19 该流程已完成并停止：10 轮、30 场、25 张团队地图、336 车次，16,393 个样本无采样缺口、丢弃或跳过行。16 场正常达到时限，14 场按胜负条件提前结束；每轮报告、原始窗口与源码差异位于 `state/cpu-arena/01/`～`10/`，总报告为 `state/cpu-arena/report.md`。最后三场实际加载 revision=20，最终源码为 revision=21，最后调整尚无后续对局。长转向、窄路拥挤、短时高频进退和更新峰值仍有记录，详细窗口及生效范围见总报告。

## 驾驶评测

`npm run ai:drive-eval` 在模拟时钟上运行团队模式纯 CPU 对局，人数取地图上限与 12 的较小值，按房间轨迹相同的 500 毫秒间隔采样。默认地图为 3、19、8、9、15、17、2、6，各 300 秒，三个进程并行；`--maps`、`--seconds`、`--concurrency` 和 `--output <文件>` 可调整，`--root <检出目录>` 使用另一份源码运行，用于新旧策略对照。

| 指标 | 口径 |
| --- | --- |
| 进退反转 | 相邻采样前后方向直接相反的比例，分母为前一采样有移动的样本对；转向反转同理 |
| 倒车占比、最长倒车、超过 4 秒的倒车段 | 移动采样中的倒车比例，以及同一条命内连续倒车的时长 |

未参与调参的 8 张图单独比较时，1 秒内回摆由每车每分钟 66.0 次降为 12.9 次，最长倒车由 12.5 秒降为 8 秒，超过 4 秒的倒车段由每车每小时 24.9 次降为 3.7 次，有目标发呆由 1.00 秒降为 0.49 秒。真人记录在地图 3、14 的 500 毫秒进退反转为 9.091%、12.369%，新版略低于该记录。命中率和输出下降来自新目标的瞄准误差；双方均为 CPU，死亡同步减少。

回摆按画面车身统计。类型 1～3 车型行进中点按转向键时，车身先向转向侧多转，松键后回到行进方向，单侧的一次修正也计为一次回摆。地图 8、15 各 90 秒抽查中，前后一秒内左右转向键交替的回摆由 2190 次降为 277 次，新版其余 253 次为这种单侧修正。

500 毫秒转向反转按按键符号统计。倒车时转向键使车头反向转动，原地转向或前进弧线接倒车弧线时按键反号而车头仍沿同一方向转动。地图 3、8、15 各 150 秒抽查 4694 对转向采样，按键反转 1041 对（22.2%），车头实际改变转动方向的 444 对（9.5%），其余为这类换挡衔接。

队友拥堵按一秒内位移不足 4 单位计算，包含原地转向。地图 9、24 各 150 秒抽查的 52 个拥堵采样中，36 个正在让行，6 个沿路线原地转向；完全停住的 8 个中 6 个目标可见，为停车射击。

控制器耗时在地图 8、120 秒对局中两版同时运行两次，`BotController.input` 每个世界更新分别为 22.7、13.7 毫秒与 22.5、15.7 毫秒，两版接近。评测机为共享虚拟机，绝对耗时包含其他负载，批量评测的更新耗时不作新旧对比。

## 已知限制

转向按键反转仍高于真人记录的约 4%，车头实际反向约为 9.5%，主要来自沿路线行驶中的小角度修正和让行。路线检查按车体对齐路线方向采样，与实际车头和高度步进不一致的窄口仍会造成短时受阻，由规划器试探与出口处理。地图、车型和出生位置随机，受阻、拥堵、往返这类小指标受个别事件影响明显，单批结果只作方向性比较。本节为服务端 World 模拟实测，尚无真人参与的对局体验评估。
