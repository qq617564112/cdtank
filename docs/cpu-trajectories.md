# CPU 轨迹与脱困

CPU 沿普通输入、权威导航和碰撞结果移动。Mistreevous 选择战术意图，控制器负责目标保持、分帧寻路、破障、队友让行及受阻恢复。

普通寻路、让行、破障接近和战斗走位均允许前进或倒车。路点落在车后方时可以保持车头、倒车接近；前后方向在 72°／108° 之间保持，避免侧向路点导致频繁换挡。可旋转炮塔始终按世界目标方向独立瞄准，预测射击使用移动后的车体朝向和本帧炮塔转动。停车交战且没有待执行路线时，若炮口偏差较大，合法的同向车体转动会协助炮塔更快对准；固定炮塔车型继续使用车体瞄准。

## 脱困与目标保持

- 单次局部脱困最多持续 1.5 秒，离开起点 36 单位后结束；持有的移动命令受阻时转入重规划，间隔 2.5 秒再尝试局部脱困。
- 合法原地转向持续缩小预定行进方向与路点的夹角时，保留路线，让慢速车体完成对齐。该过程仍记录物理停滞时间，但不触发局部脱困或局部循环重规划；连续移动受阻仅按最终发出的平移输入计时。移动权限关闭期间暂停脱困计时，恢复后从实际位置继续观察。
- 追击不可射击目标或执行避让、离开动作时，若 8 秒仍未离开半径 96 的区域，触发重规划。正常停车射击及等待已摧毁障碍物释放碰撞不计入此追击停滞条件。
- 局部移动优先减少队友拥挤，降低重复经过旧位置和立即反向的优先级。脱困期间保留普通路线，普通寻路继续推进。
- 撤退由近距离威胁触发，持续到偏好的交战距离；途中暂时被墙角遮挡的同一威胁仍保留。退出后只有再次进入较近的危险距离才重新撤退，避免在视线边缘每帧切换撤退和追击。
- 重规划尝试半径 144、72、36 的可达出口，重复尝试改变方向次序；同时请求破障。尚未完成且没有可用路径的普通搜索，以及正在推进的破障搜索保留计算进度，继续使用各自已有的 8 秒搜索时限。
- 有效目标至少保持 2.5 秒，之后最多每 1.5 秒评估一次替换。新目标须近至少 160 单位且距离小于原目标的 70%；已有任务时，仅允许进入近距离威胁范围的敌人按此规则替换。队伍重新分工需要保持目标至少 6 秒、原目标多出至少两个同伴负责，且当前没有路线或脱困任务。
- 目标失效、临时不可达及敌方 VIP 优先规则继续生效。切换敌人时保留已经选择的避让和离开目的地。
- 同队通道让行优先向行进方向右侧腾出空间，再尝试左侧及其他出口；无法独自离开的队友会请求先行者协助。对外预留下一路点，随后才使用远处终点。

## 记录与分析

房间子进程在有 CPU 或托管玩家的正式比赛中每 500 毫秒采样一次，默认写入 `state/cpu-traces/<房间号>.ndjson`。`CPU_TRACE_DIR` 可指定目录。每 2 秒异步写盘；单文件上限约 8 MiB，保留 `.1`、`.2` 两份轮转文件，待写队列上限 1 MiB。写盘失败会在服务日志报告并停止该房间的记录。

样本包含房间、回合、地图、战斗时间、实体 ID、显示名、车型、队伍、位置、输入、生命状态、移动权限、目标和破障物 HP，以及以下控制器字段：

| 字段 | 含义 |
| --- | --- |
| `targetChanges`、`targetSelectedAt`、`targetChangeReason` | 目标变化次数、最近选定时间与原因 |
| `driveReversals` | 逐次决策累计的前后进退切换次数 |
| `policyRevision`、`driveSource`、`retreatThreatId` | 实际加载的策略版本、本帧驾驶分支和持续撤退对应的威胁；`AIM_ASSIST` 表示停车时车体协助炮塔瞄准 |
| `stalledSeconds`、`blockedSeconds` | 局部物理进展计时与连续移动无位移计时 |
| `routeStalledSeconds` | 本轮追击尚未离开 96 单位区域的时间 |
| `recoveryReplans`、`recoveryReason` | 强制重规划次数与最近原因：尝试超时、命令受阻、没有出口或局部循环 |
| `searching`、`breachSearching`、`breachWorking` | 普通搜索、破障搜索及破障任务状态 |
| `path`、`goal`、`waypoint`、`avoidance`、`escape` | 前四个路点、终点、队友预留点和局部移动目的地 |

`tickTiming` 汇总采样间的更新次数、耗时、超预算次数与最大更新间隔。`droppedSamples` 记录队列溢出，分析时同时核对采样缺口。

```sh
npm run ai:analyze -- state/cpu-traces/R1.ndjson* --output /tmp/cpu-analysis.json
```

分析按进程会话、房间和回合分组，输出逐车统计、疑似异常时段及热点。异常时段是初筛：需结合目标是否可射击、破障 HP、周围队友和原始位置，区分停车交战、等待碰撞释放、短暂同行与持续受阻。`targetChangeReason`、`recoveryReason` 是最近一次变化的原因；500 毫秒采样可能跳过中间事件，累计次数可用于判断采样间发生了多少次变化。

## 已有证据与待确认范围

2026-10-15 的 R1 第 1 局为 0008 废弃魔王路，1 名真人和 11 个 CPU，共 594 个样本。P5、P10、P12 分别在很小范围内持续受困约 242、97、72 秒，脱困不断覆盖正常规划；同局还出现有效目标反复切换和短暂队友拥挤。原始记录与逐车分析位于 `recovery/output/perf/cpu-trace-2026-10-15-r1/`。

当前调整针对这些实际行为。新对局仍需确认长时间局部循环是否消失、受阻后寻路和破障是否继续执行、队友是否能够通过通道，以及更新耗时是否变化。现有比赛数据属于调整前，不能作为调整后的效果证明。

服务端从源码启动时，新建房间进程会加载当前控制器；已经存在的房间保留启动时的代码。浏览器训练模式在 Worker 内使用同一控制器，轨迹文件由服务端房间记录。

## 十次逐局优化循环

`scripts/cpu-optimization-loop.ts` 只读账户数据库已经提交的 `match_history`，以真实结算作为对局完成信号。它每 2 秒查询一次新记录，将同一比赛的多个账户战绩合并，再按房间、回合、地图、模式及结束时间从轮转轨迹中提取对应进程会话。结算后等待正常异步写盘，轨迹必须覆盖到结束前 3 秒内。

```sh
npm run ai:loop -- wait
npm run ai:loop -- status
```

首次运行从当前时间开始领取新结束的比赛；`--since <毫秒时间戳>` 可指定起点。状态保存在 `state/cpu-optimization/status.json`，重跑继续原有计数。`--directory` 可指定独立的记录目录，`--database` 或 `ACCOUNT_DB_PATH` 可指定实际服务使用的账户库，`CPU_TRACE_DIR` 与服务端的轨迹目录保持一致。

`wait` 遇到一场尚未处理的新比赛后，保存 `01/`～`10/` 下的原始轨迹、离线分析、比赛元数据和优化前 CPU 源码，然后输出 `MATCH_READY` 并退出。由当前会话等待的工具调用接收退出结果，继续分析和实施优化；脚本不启动第二个模型会话，也不自行生成修改。当前会话的持续目标负责重复调用 `wait`。

每次优化以本局真实行为为依据，逐辆排除正常交战、转向、权限限制、破障等待和重生，再改善进退保持、转向收敛、避障、目标保持及让行。以自然、顺畅、接近真人操作为目标，不通过放宽碰撞、移动权限或战斗规则消除异常。

分析和修改完成，并确认新代码的应用状态后记录一次完成：

```sh
npm run ai:loop -- complete --report state/cpu-optimization/01/report.md \
  --applied '记录实际加载新版 AI 的进程、版本或生效范围'
```

`complete` 要求报告非空，并比较领取比赛时与当前的 CPU 源码；没有实际 AI 改动不会增加次数。它保存 `changes.diff`、修改后源码、应用说明和完成时间。尚未确认完成的比赛保持 `pending`，再次 `wait` 返回同一任务，不重复累计。每次串行完成后再领取下一局，累计 10 次输出 `STOPPED`，以后不再领取。

修改后的真实比赛才用于评价效果。已有房间不会因写入源码而自动更新；应用说明必须区分已经加载新版的房间与仍在使用旧实例的比赛。持续目标的会话需要保持可运行，外部脚本退出本身不具备向已经关闭的 Codex 会话投递消息的能力。
