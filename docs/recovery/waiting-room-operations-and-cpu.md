# 等待房间操作与CPU管理

M5-03/UI-44：正式等待房间沿800×600基准缩放，原十二个源名单槽继续显示权威成员、队伍与准备状态，超出源槽的成员显示在overflow区域。源Ready、CancelReady、ChangeTeam、Invite与Leave继续调用既有房间接口。

等待页侧栏显示已确认的房名、房号、模式、地图、时限、人数、准备人数、密码与友伤状态。CPU区域显示当前CPU数量、名称和已配置的有效配给槽数，并容纳既有CPU添加、移除、配给与托管操作。此侧栏是Web界面装配，原room_main控件和图片继续沿源区域呈现。

操作状态区区分资源载入、请求等待、失败、邀请确认和正常状态。Ready、取消准备、换队、邀请与离房请求持有自己的操作名称，完成后按既有页面代际清理；异步失败沿原通知对话框显示。请求期间继续禁用重复提交，界面读取权威快照。

所有动态文字由全局附件字体消费。CPU管理、状态与overflow区域随同一viewport scale缩放，键鼠隔离和原通知/退出路径继续复用现消费者。

## HTTP新增CPU

等待页点击新增机器人时调用 `POST /game/api/rooms/:roomId/cpus`，请求头为 `Authorization: Bearer <账户token>`，JSON 请求体包含：

| 字段 | 用途 |
| --- | --- |
| `requesterPlayerId` | 当前操作玩家的房间成员ID |
| `round` | 当前局号 |
| `tankId` | 可选的有效战车ID，沿用房间创建CPU的参数 |
| `team` | 可选的猫队0或狗队1 |

服务端从已登录且仍连接的WebSocket会话核对token、房号与操作玩家，不查询账户数据库。实际添加继续由房间进程的 `manageCpu` 执行，保留房主、当前局号、等待阶段、房间人数和队伍容量规则。CPU角色与配给保存于房间内存。

添加完成后HTTP立即以201返回 `{round, playerId}`，其中 `playerId` 为新CPU的ID。按钮收到响应即结束请求等待，不等待下一次快照。参数错误为400，未登录为401，房间成员不匹配为403，业务冲突为409；错误体统一为 `{error: {code, message}}`。

HTTP响应只包含操作结果；成员、队伍与准备状态仍由既有 `RoomSnapshot` WebSocket链路更新，周期与接收逻辑沿用现有实现。CPU移除、配给和托管继续使用既有接口。

服务端在同端口优先处理HTTP接口，再托管静态网页。HTTP复用 `/game` 反代入口：Vite去掉此前缀并保留后续路径，转发到 `CDTANK_GAME_SERVER` 的HTTP地址；独立静态网页部署见 `deployment/nginx.conf.example`。服务端同时处理直连的 `/game/api/rooms/:roomId/cpus` 和反代后的 `/api/rooms/:roomId/cpus` 路径。

客户端读取响应正文后解析操作结果。空正文、非JSON正文或成功结果字段不完整时提示查看房间状态，不自动重发新增请求。运行服务端必须包含接口实现；源码更新后需要重新编译并重启服务。

## 操作等待

房间进程的库存查询、配置资格、输入序号和退出处罚计数查询只回传结果，不构造整房快照；只读回包可以先于尚未发送的tick回包发送，状态发布和事件的顺序保持原样。修改房间状态的命令仍先更新网关缓存，再完成请求，离房关闭与角色变化所需的快照沿用原路径。

离房请求按房间串行，不同房间不共享等待队列；同房间的报价、处罚确认和退出仍按顺序执行。建房、加入和快速加入的账户库存、角色来源、装备与称号合并为一次内部命令，绑定顺序保持原样。

装备保存直接采用确认回包里的装备绑定，更新受影响物品的安装状态，不再等待额外的库存和拥有角色查询。选择出击战车直接采用确认资料。后台资料刷新按页面代际和操作版本更新，较早的刷新结果不会覆盖后续保存。

修改等待房间时，同地图且尚未开战的房间复用战场索引。更换地图或编辑已结束对局的房间仍重建战场，保留原有准备状态清理和局号推进。

编辑已结束对局的房间时，局号推进与快照tick清零同时完成。随后全员准备进入资源载入阶段时，同一局号的tick保持为0，客户端按局号和tick过滤旧快照后仍能接收载入状态并提交资源就绪确认。
