# WebGPU 实例缓冲与 mipmap 初始化

战斗、我的家和模型预览通过共同的 WebGPU 引擎入口安装容量检查与贴图初始化提交。手机和电脑共用，Babylon.js 固定为 9.29.0。

## 实例缓冲容量

Babylon 的自定义实例属性共用 CPU 数组，WebGPU 为每个 render pass 分别保存 GPU 顶点缓冲。原生扩容只释放当前通道的旧缓冲；另一通道随后使用变大的 CPU 数组时，可能向较小的 GPU 缓冲写入越界数据。

现场植物 `obj05416` 的源网格 `plane507/0` 有 82 个实例，`plantSway` 每条数据为 2 个 float：

| 数据 | 字节数 |
| --- | ---: |
| 共享 CPU 数组 | 1024 |
| 动态模糊几何通道 GPU 缓冲 | 1024 |
| 主相机 GPU 缓冲 | 256 |
| 绘制 82 个实例需要的属性数据 | 656 |

WebGPU 记录了写入和绘制越界，随后拒绝提交渲染命令，世界画面变黑而 HUD 仍显示。通过 Babylon 公共接口重新注册该实例属性、保留全部实例值后，现场世界画面恢复。

`webgpu-instanced-buffers.ts` 在原生 `_processInstancedBuffers` 前检查当前通道已有自定义属性缓冲。GPU 容量小于共享数组的字节数时，仅释放该缓冲并清空引用，由 Babylon 原生流程重新创建、填入实例值和绑定。其他通道继续保留自己的数据，实例排序、裁剪与摆动规则不变。

## 贴图初始化提交

现场炮塔贴图 `001U_001.webp` 的基础层为 1600×1600，GPU 与原图的 32×32 个采样点完全一致；读取的 mipmap 第 1–6 层全部为零。第 1 层为 800×800，共 640000 个零值像素。调用 Babylon 原生 `updateSamplingMode(existingMode, true)` 后，第 1 层非黑像素变为 524045，炮塔外观恢复。

Babylon 使用直接队列操作上传图片基础层，首次 mipmap 生成则记录在 upload encoder。帧结束时 upload 和 render 命令缓冲一起提交，任一渲染命令缓冲无效都可能导致整个提交被拒绝。原始错误已记录有效 UploadEncoder 与无效 RenderEncoder 同批提交。

`webgpu-texture-uploads.ts` 在原生 `createTexture` 返回后，为带 mipmap 的 InternalTexture 安装一次性加载监听，已就绪的纹理直接设置标记。图片加载后在 `onBeginFrameObservable` 中通过原生 `flushFramebuffer` 提交初始化命令，再开始场景绘制。同一帧前加载的图片集中处理；无新贴图时不执行额外提交。设备恢复直接重建 InternalTexture 的路径也使用同一入口。

坦克默认图、车身和炮塔换装图、履带全部动画帧均通过 Texture 加载，模型外部和内嵌图片也由该入口覆盖。原生 mipmap 生成、过滤与各向异性采样继续使用既有设置。

## 通道释放与资源重建

Babylon 9.29.0 的实例销毁流程只遍历共享属性缓冲和各通道当前矩阵缓冲，遗漏了各通道的自定义属性缓冲、上一帧矩阵缓冲。网格 `_rebuild` 同样没有清理各通道自定义属性缓冲。`webgpu-instanced-buffers.ts` 在销毁和重建前调用原生 `_releaseRenderPassId`，完整释放通道资源，再继续原生流程。

切换动态模糊、重建几何目标时，引擎释放旧通道，只遍历场景中的网格。地图复用的源网格可能留在 AssetContainer 中，场景里只有它的实例。实例释放通道时同时通知其源网格，并清除源网格该通道的 draw wrapper，避免切换设置后保留旧缓冲和绑定。

WebGPU 设备丢失后的原生恢复入口传入异步 `initAsync` 回调，但基类未等待该回调就开始重建。WebGPU 的 `_rebuildBuffers` 还遗漏了普通场景与 UtilityLayer 场景的几何重建。`ResourceWebGpuEngine` 等待设备初始化完成，再调用原生恢复流程；重建缓冲时先调用两类场景的 `_rebuildGeometries`，再继续原生 UniformBuffer 与 storage buffer 重建。设备恢复失败时记录错误，保持渲染暂停。

MV3 与破损地图模型的克隆会让模板几何同时留在场景和 AssetContainer 中，两者在设备恢复时都会调用几何 `_rebuild`。原生重建直接替换缓冲句柄，重复调用会重复上传和分配。`webgpu-geometry-rebuild.ts` 检查索引及全部顶点属性对应的原生缓冲，只有它们都已属于当前 WebGPU 设备时才跳过重复重建；任何缓冲缺失或仍属于旧设备时继续原生重建，空几何也保留原生行为。WebGPU 每次初始化使用新的 `uniqueId`，不影响下一次设备恢复。

相关范围覆盖植物、重复地图模型、动态模糊上一帧矩阵、HUD、粒子和后处理几何；不改变正常渲染时的缓冲布局、分辨率或采样配置。

## 横向核查

HUD 与粒子批次已在扩容时替换完整顶点缓冲，恢复时重新上传完整容量；CVD 帧纹理和形变纹理不生成 mipmap，上传数据尺寸固定；实例世界矩阵的 CPU 与 GPU 容量按通道保存。这些路径没有发现与此次共享容量扩容相同的问题。

## 验证范围

现场恢复证据对应植物缓冲重建和炮塔 mipmap 重新生成；尚未逐次捕获炮塔首次 mipmap 命令与植物越界的提交关联。车身及履带采用相同的贴图初始化修复，但没有分别记录恢复前后的像素统计。

生命周期与设备恢复遗漏依据本地 Babylon 9.29.0 源码和项目调用路径确认，没有设备丢失现场采样。代码改动完成源码核查。按仓库约定未运行测试、构建、类型检查或浏览器验收；尚无改动后重新加载、切换动态模糊、换图或设备恢复的实测结果。
