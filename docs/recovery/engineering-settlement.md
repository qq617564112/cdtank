# 服务端结算职责

E-02将既有对局结果计算收拢到`apps/server/src/settlement/match-result.ts`。输入只有玩家结算数据、模式、地图输赢平奖励、队伍剩余生命/积分、本局编号、结束时间、原因及可选赢家；输出仍是共享协议的`MatchResult`。模块不依赖World内部类型、账户存储、房间广播或战斗状态。

## 结果规则

- 排名先比较击杀数，模式5改比较摧毁目标数，再比较未取整的战斗分；完全同分保持原玩家顺序并共享名次，后续名次按排序位置计算。
- 模式1按队伍剩余生命、模式2按队伍积分确定赢家，队伍数值差小于`0.000001`时平局。模式3使用玩法传入的赢家；模式4/5按排名首位与次位的指标、战斗分决定个人赢家，完全同分为平局。
- 明确传入的队伍或个人赢家保持优先，包括弃局和目标达成产生的结果。没有队伍或个人赢家时，所有玩家取得平局结果和地图平局奖励。
- 战斗分使用`Math.round`，总分为取整后的战斗分加地图奖励。排名仍使用取整前的战斗分。
- 结束消息仍优先显示个人赢家名称，否则显示猫队、狗队获胜或本局平局。

## 生命周期边界

`settlement/finish-round.ts`负责`PLAYING`的一次性提交门槛：先计算结果，再同步设置`FINISHED`、结束时间和赢家，清空弹丸、为所有玩家写入独立的空输入并保存结果。重复调用返回false，不覆盖时间或结果。World仅在实际完成提交后补充可加入房间；再战重置、投票、离房、CPU清理和快照仍通过既有入口运行。

模块直接修改正式房间状态，不保存第二份状态；伤害回调返回前已提交，所以同一tick的弹丸循环立即读取FINISHED并停止。计算规则仍在match-result纯函数中，冻结提交不接账户奖励持久化，也不把重建结果规则当作原程序规则依据。

## 验收

结果计算迁移的以下三项均通过；提交迁移的独立验收证据见下文。

- `npx tsx tests/match-rules.cts`：五模式玩法、准备门槛、截止冻结、个人赢家、原目标碰撞、弃局、一次性结算和再战。
- `npx tsx tests/autopilot-match.cts`：五模式CPU及本人托管以普通50ms输入连续两局，验证自然终局、结果冻结、再战、库存持续消费及最后真人离开后的清房。
- `npm --prefix apps/server run typecheck`：检查结算输入和现有World、共享协议的类型衔接。

## 验收范围

上述对局验收使用模拟时钟和正式World规则。它们覆盖服务端结算与生命周期，没有提供网页视觉或原程序玩法一致性的新增证据。

提交迁移补充tests/match-rules.cts的决定性命中全部输入同步冻结、重复tick保持结束时间、截止前排队输入冻结断言。命中/原目标碰撞、五模式冻结/弃权/再战、自然治疗与CPU两局、正式服务端构建/类型、188可达模块边界通过，日志engineering-finish-{build,match,terrain,healing,types,boundaries}.log。编译真实联机重启保存和CPU五模式各两局也通过（engineering-finish-compiled.log）；正常网页资源失败重试、准备、实际渲染/CPU运动及退出通过（engineering-finish-browser.log）。
