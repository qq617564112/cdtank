# CDTank 复活路线评估与执行计划

日期：2026-10-01。依据：本地客户端的静态分析、实际解包与表格导出，以及 Babylon.js / TSRPC 官方资料。本文是推荐计划；尚未确认公司的交付期限、人员、目标设备及是否强制兼容原 Windows 客户端。

## 结论

**如果目标是尽快交付可演示、可持续开发的新版本，推荐 Babylon.js + TypeScript/Node + TSRPC 重建核心玩法，复用原资源与数值，按需逆向关键行为。**

**如果目标是原 Windows 客户端无需重做就能重新联网，必须走兼容服务端路线。** Web 重建无法满足这个验收条件。若要求所有旧功能、手感和表现完全一致，Web 全量重建也可能比协议兼容更费工，当前没有证据支持它一定更便宜。

当前推荐成立的关键是“允许分阶段恢复”。Web 版可以先交付移动、射击、两人对战；旧客户端对服务端响应、认证、初始化数据有既定要求，缺失一个前置环节可能使后面的原有功能根本无法进入。

## 已经验证的事实

运行 `recovery/inspect_assets.py` 得到以下结果。数量不包含额外 download 补丁目录；包内已删除/废弃条目未作为有效资源导出。

| 材料 | 实际恢复结果 | 对路线选择的价值 |
| --- | --- | --- |
| Data/data.cpk | 4,459 个有效文件、260 个目录，解压后约 233 MB | 原素材可提取，不必全部重新制作 |
| Data/music/music.cpk | 14 个 MP3，约 24.5 MB | 音乐可复用 |
| DDS | 2,601 个，全部通过 Pillow 实际解码 | 贴图转换不是主要未知项；仍须处理色彩、透明和材质映射 |
| XML | 69 个，全部通过 XML 解析 | 可参考界面结构；CEGUI 布局不能直接成为 Web 界面 |
| 游戏数据表 | 24 张、4,201 条数据记录，导出 UTF-8 JSON 和带 BOM 的 CSV | 可恢复名称、描述、数值配置和部分规则参数 |
| 战车/技能/道具 | tank 21 条、skill 342 条、item 204 条 | 有较完整内容材料；不等于实现了攻击公式和技能效果 |
| 地图 | 25 组 `.obj/.nav/.box/.cas/.ctl/.rpt`；5 张模式配置表共 26 条记录 | 模式表记录有重复地图，不能相加当作独立地图数量 |
| 模型 | 745 个 `.mv3`、81 个 `.cvd`、10 个 `.3ds` | MV3/CVD 转换仍需攻关，3DS 的存在不说明战车一定有标准格式副本 |
| 游戏网络库 | ObjNet 发送/接收使用 u16LE(payload长度)+payload | 已定位传输帧，但没有恢复业务字段及状态机 |
| 登录依赖 | client.dat 中有 Login/Lobby/Room 配置；QQLogin 有单独腾讯登录链 | 原客户端恢复还涉及认证与启动环境 |

具体示例：tank 表的第一辆“小勇士”包含 TankAtk=100、TankDef=15、TankMove=10 等原始字段；m001 表的“田野路”包含 Time=300、PlayerMin=4、PlayerMax=10 等参数。字段值的物理单位、缩放、应用公式仍需验证，不能直接解释为米/秒或最终伤害。

**地图 `.obj` 是自定义二进制场景记录，起始内容出现 `SYcScnObjBreach`，不是 Wavefront OBJ 文本。** 将它改后缀或直接放入模型加载器不会完成转换。

CDTank.exe 的 PE 时间戳对应 2006-09-04 UTC；它只是文件头元数据，不能单独证明完整发行版本。目录中的 RPGViewer Readme/FAQ 是第三方工具说明，不能视为原游戏设计资料。

## 两条路线难在哪里

| 比较项 | Babylon.js + Node/TSRPC 核心重建 | 逆向协议 + 兼容服务端 |
| --- | --- | --- |
| 客户端开发量 | 较大：控制、相机、渲染、UI、反馈全部需要实现 | 较小：原客户端保留画面和交互；有旧系统兼容工作 |
| 模型/地图 | 必须转换或为首版制作替代资产；当前最大前期风险 | 通常无需转换，原引擎自行加载 |
| 协议 | 自定义新契约，可以逐步扩展 | 必须满足旧客户端既定格式和消息顺序 |
| 认证 | 可从游客身份开始 | 要处理游戏登录及旧 QQ 启动依赖，细节尚不完整 |
| 战斗规则 | 要重建；首版可明确简化规则 | 同样需要重建，且可能必须匹配客户端预测和校验 |
| 缺少运行中服务端的影响 | 可以独立推进开发 | 无成功会话作为对照，只能反汇编、调试、构造响应验证 |
| 阶段展示 | 可从资源查看、单人移动、双人对战连续交付 | 很可能先卡在登录/大厅，出现投入很多但没有可玩画面 |
| 原版一致性 | 需要逐步校准，不可直接承诺 | 表现更容易保留，玩法和服务端规则仍不保证一致 |
| 工期可预测性 | 范围受控时相对高，模型转换要先验证 | 相对低；初始化、状态同步、加密等发现会改变后续工作量 |
| 长期维护 | 新代码、现代浏览器、可测试的规则模块 | 新服务端加旧二进制的兼容边界，需要持续保留逆向知识 |

“写个收包服务器”并不等于恢复游戏。至少还缺：业务消息号及字段、登录响应、角色和背包初始数据、大厅/房间流程、战斗同步与生命周期、掉线处理、结算和持久化。

旧 EXE 中有 NOS、TCP、RUDP、NAT 穿透相关字符串；它们是追踪线索，尚未证明每一条路径都由这款游戏实际使用。不能据此直接确定战斗是 UDP、P2P 或服务器权威，也不能给出完整网络重写报价。

## 推荐策略：资源与规则恢复为共同基础，Web 为交付主线

1. 保存原客户端和压缩包，用哈希记录证据；所有转换输出与原件分开。
2. 原资源只读提取，生成内容清单、可读配置、模型转换工具和素材映射。
3. Web 首版选择桌面键鼠、单地图、单战车、一个简化对战模式。两人是技术验收人数，不代表原模式允许两人；差异要明示。
4. 只逆向影响首版的行为：坐标/尺度、移动转向、射击间隔、碰撞、弹丸、伤害、重生、相机。能从数值表得到的配置不重复猜测；无法证实的规则记为“重建规则”。
5. 等首版可玩，再依照原素材和证据逐步增加内容。商城、宠物、交易、账号成长不能与第一局对战同时启动。
6. 旧客户端兼容服务端保留为备选研究方向，设置独立限时验证；不维持两套完整游戏实现。

### 前五个工作日的验证与止损

| 验证 | 产物 | 通过条件 | 未通过时的决策 |
| --- | --- | --- | --- |
| 资源转换 | 一辆战车 GLB、贴图 PNG、一个场景或局部场景 | 方向、比例、材质正确，浏览器可载入；炮塔/车身可独立控制或有明确替代 | 第 3 天仍无可用模型则先交付代理模型玩法，并明确原美术恢复延期 |
| 地图转换 | 原场景记录到标准场景描述和碰撞代理 | 至少一张地图的实例位置可检查，视觉与碰撞信息能分开 | 第 5 天仍不能转换则选小范围场景重建，重新估算美术还原成本 |
| 玩法参考 | Windows 本地运行记录、截图/录像或指定函数的静态证据 | 得到至少输入、相机和战车运动的可复核参考 | 服务端缺失导致无法进入战斗时，以重建规则继续，不宣称复刻原手感 |
| 兼容路线备选（最多 2 人日） | 登录首包字段说明与一次可复现的本地状态推进 | 有实测或代码链支持的字段、响应和下一状态 | 无突破就停止首版旧协议工作；只发现包长格式不算通过 |

这些是预算上限和调整点，不是对五天内一定能完成转换的保证。如果公司强制使用原客户端，备选验证应改为主线，Web 计划不再适用。

## Web 架构边界

```text
原始文件 → 解包/解表 → 内容清单与转换资产
                        ├→ GLB/贴图/音频 → Babylon.js 渲染
                        └→ 验证后的数值/地图碰撞数据 → simulation

浏览器输入 → TSRPC WebSocket → Node 房间 → simulation → 权威快照/事件
浏览器展示 ← 插值/本地预测与校正 ← TSRPC WebSocket ← 房间广播
```

- `apps/web`：Babylon.js 渲染、相机、键鼠输入、音效、HUD、远端插值。首版使用 WebGL，避免把 WebGPU 或手机适配变成前置条件。
- `apps/server`：游客会话、房间生命周期、连接归属、频率限制、战斗 tick、断线和结算。首版单进程多房间，暂不拆微服务。
- `packages/protocol`：TSRPC 请求/响应和消息契约。控制流程用 API，连续输入与快照用消息；固定依赖和生成工具版本，验证浏览器与服务端组合。
- `packages/simulation`：不依赖 Babylon.js 和 socket 的规则模块。固定步长、显式配置和随机种子，可进行输入回放和确定性测试。共享模块不表示网络两端必须做完全一致的锁步模拟。
- `packages/content`：稳定实体 ID、来源记录、单位转换、战车参数、地图碰撞代理；原始表不未经验证直接进入计算。
- `tools/assets`：CPK/数据表、DDS、MV3/CVD 和场景转换工具。CPK 恢复已验证，MV3/CVD 转換尚未完成。

建议初始契约：`GuestLogin`、`CreateRoom`、`JoinRoom`、`SetReady`、`StartMatch`；`PlayerInput`（序号、目标 tick、移动/瞄准/射击）、`WorldSnapshot`（服务端 tick、输入确认号、实体状态）、`MatchEnded`。这些是新协议设计，不是旧协议恢复结果。

客户端只能请求操作，不提交最终坐标、伤害或胜负。服务端验证输入与连接身份，计算移动、弹丸、命中、生命和分数。首版用适合场地和玩法的简单碰撞代理；先测原始玩法是否需要弹道高度、地形坡度、掩体和可破坏物，再选完整物理引擎。

建议从 simulation 30 Hz、快照 10–15 Hz、渲染随设备帧率起步；这些是待压测参数，不是恢复到的原始频率。WebSocket 有可靠有序传输及丢包时的队头阻塞风险，需要限制发送队列、丢弃尚未发送的过期快照，验证延迟和带宽。不把“换成 TSRPC”视为自动解决预测、校正和战斗同步。

TSRPC 官方说明支持 TypeScript 契约、运行时类型检查、二进制序列化、HTTP/WebSocket；它不提供这款游戏的房间、物理、命中和反作弊规则。类型检查也不能代替语义检查，例如射速、距离和玩家归属。

## 六个依赖有序的迭代

本计划的首版边界：**桌面浏览器两名玩家进入房间，在一张地图用一种战车完成移动、射击、命中、死亡/重生和一局结算。** 不包含商业运营版，不承诺所有旧行为完全一致。

| 迭代 | 目标与底层/服务端先行 | 前端跟进 | 验收与范围 |
| --- | --- | --- | --- |
| 0：资源与证据 | 内容 ID/来源/数值校验；转换一个模型和一张地图；确认坐标、尺度和碰撞数据 | 浏览器资源查看页，相机旋转查看模型和场景 | 能复现导出，贴图可读，原资源/替代资产明确；暂不做完整大厅 |
| 1：单局模拟 | 独立 simulation，实现战车移动、转向、射击、弹丸和简单碰撞；固定步长 | 加载模型/代理模型，键鼠操作、相机和基本反馈 | 固定输入回放结果稳定，无穿墙和无限射速；暂不做宠物/技能树 |
| 2：连接和房间 | TSRPC 契约、游客会话、房间/准备/开始；房主退出和重复请求语义 | 最小进入/创建/加入/准备界面 | 两个独立客户端能进入同一局，连接与玩家一一对应；暂不做永久账号 |
| 3：双人战斗 | 权威 tick、输入序号、状态广播、射击/伤害验证、断线清理 | 本人预测/校正、他人插值、命中/死亡反馈 | 两端位置和生命最终一致，输入越权被拒；暂不扩展成全地图/全战车 |
| 4：一局闭环 | 重生、计时/计分、结束条件、临时战绩与可回放事件记录 | HUD、结算、返回房间、再开一局、声音 | 可连续完成三局，双方结果一致；暂不做商城/交易/付费 |
| 5：交付与稳定性 | 配置化启动、日志、资源版本、压测和最小部署；持久化只存需要的试玩结果 | 加载进度、断线提示、桌面浏览器兼容、性能优化 | 新环境可启动；目标设备与网络下可验收；手机/WebGPU/跨区运营后排 |

迭代 0 是资源路线检查点；迭代 1 是规则模块检查点；迭代 3 是联机可玩检查点；迭代 5 是首版交付检查点。依赖顺序以表格为准。内容转换与独立模拟可以在接口明确后分别推进；前端网络集成必须等待房间与快照契约明确。

重点验证：simulation 的移动/碰撞/射速/伤害回放；房间的连接归属及退出；两个真实浏览器的完整一局；100–200 ms RTT、少量丢包和短时断线条件下的校正与快照积压。先用两名玩家验收，再按产品需要扩到 4–10 人测试，不能从“两人跑通”推断运营容量。

## 工期和对外承诺

以下是预算讨论用区间，不是已经实测的交付承诺。假设一个熟悉 TypeScript、实时网络和 3D 工程的全职工程师，可获得原版操作参考，首版一张图一种车且允许简化，资源转换验证成功：

- 资源/规则/网络验证：先预算 3–5 工作日；未通过则重估。
- 核心 Web 可玩演示：约 3–6 周，可能使用代理模型和简化场景。
- 原素材与完整一局结合、经过基本稳定性验证的首版：约 6–10 周。
- 如果工程师需要同时学习 3D、网络同步和资源逆向，以上区间不适用，应以第一周实测吞吐重新估算；不能承诺单个新人一个月交付完整网游。
- 兼容服务端：先预算 3–5 工作日做登录/消息状态推进验证；未通过之前不承诺完整对战日期。即使先进入大厅，战斗和数值一致性仍需另一次估算，不把大厅成功当作完成一半。
- 全内容重建和可运营产品需单独路线图，不能把 24 张表、全部模型、技能、宠物、交易、支付、客服与持续运维挤进上述首版范围。

建议对老板的交付表达：

> 已确认原客户端可以恢复数千个资源和主要游戏数据。推荐先做浏览器核心对战版，第一阶段验证一辆战车与一张地图的转换，随后做两人完整对局；旧客户端兼容登录只做限时验证。首版交付的是可持续开发的核心玩法，不是全部商业功能恢复。

还需确认的产品条件：原客户端兼容是否强制、实际验收日期、可用人员/美术支持、目标电脑与浏览器、首版是否允许替代模型/简化规则。它们会改变范围和估算，不阻碍先完成转换验证。
