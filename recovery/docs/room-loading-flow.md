# 等待房间与对局资源载入

正常入房只显示原 `room_main.xml`、`default.xml`、`playerlist.xml` 与等待聊天页。地图、战车、战斗HUD、场景特效和环境声音的加载从正式开始后的 LOADING 阶段进入；准备按钮只依赖房间状态。CPU管理默认收起，右侧保留原玩家/好友面板，等待页不显示三维战场。

## 原客户端来源

直接读取 `CDTank/CDTank.exe`：`447284–44736a` 从 `data\\ui\\loading\\%d.jpg` 的五张背景中选择一张并绘制；`45a4c1` 加载 `jianpanshuoming.tga`、`tanke.tga`、`loading_1.tga` 与 `loading_2.tga`，安装 `458277` 加载回调。`4582c0–4583a4` 按已完成项/总项裁出亮色 loading 图，键位图位于144/100，loading词位于画面右下并距底30，战车图相对该位置偏左110、距底25。`4377d6` 的消息注册名是 `UMsgLoadingOver`。这些是二进制静态来源，未运行原程序。

网页复用已发布 `/Data/ui/loading/1.png` 至 `5.png` 以及以上四张TGA对应的PNG；首次加载游戏与正式对局载入共用 `interface/resources/loading-page.tsx` 和同一套样式，背景在800×600原坐标内裁切，不把1024×1024纹理的黑色填充压入画面。`BattleLoadingPage`负责提供对局状态、已载入人数、重新载入与返回大厅操作。进度按实际完成的HUD/特效目录、地图、场景声音/特效、全部角色资源及场景就绪阶段推进，完整后显示等待其他玩家。

## 当前通信与业务

房间按 WAITING → LOADING → PLAYING 执行。当前全员准备规则触发 LOADING；再战确认同样进入 LOADING。此时服务端不推进World战斗、CPU输入或比赛时限。客户端完成地图、角色动作与场景资源准备后，才发送当前局 `Ready {round, resourcesLoaded: true}`；普通准备仍发送 `Ready {round, isReady}`，两种确认分开处理。

`MatchSnapshot.loadedPlayerIds`公开本局加载确认。每个真人角色必须确认，CPU自身没有网页渲染器，由所有真人客户端加载其模型。最后一份确认完成后才初始化正式对局并设置 `startedAt`。普通输入同时受PLAYING和本机本局资源就绪约束，未加载客户端不提前移动或开火。协议附加ReqReady字段2、MatchSnapshot字段15，保留已有字段编号。

LOADING期间拒绝新成员加入及队伍/配给变更。成员正常退出或断线保留到期时，剩余成员回WAITING重新准备，清空原加载确认；客户端取消该轮资源所有权，旧异步返回不能确认下一轮。短时断线复用原房间和加载结果，恢复连接后补发本局加载确认。再战重新确认本局就绪，允许复用已加载的同图资源。资源失败保留loading错误、重新加载与返回大厅入口，不自动开启对局。

全员准备、加载确认字段及服务端屏障是当前网页业务规则；原服务端完整开局授权未由上述客户端字符串恢复。
