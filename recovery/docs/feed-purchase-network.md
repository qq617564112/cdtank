# 饲料购买网络验收

2026-10-03验收通过：实际购买、自然战斗两轮回血与结算、双客户端效果通知及有限CAS、服务重启后的余额/库存/快捷栏/重放账本均通过。金币账户购买3份后两次使用，重启恢复库存1份和金币970；代币账户恢复库存3份和代币970。

运行 `npx tsx tests/feed-purchase-network.cts`。脚本在端口3160启动独立的实际TSRPC服务，使用临时SQLite账户库，结束时关闭自身服务并删除临时库。结果写入 `recovery/output/feed-purchase-network.json`。

账户夹具显式导入已拥有的宠物、坦克和角色资料；两个购买账户各有金币1000、代币1000，余额不足账户两种余额各9，另一个账户没有角色资料。所有账户初始道具库存为空。原生角色记录来自 `role-owned-pair-native.json`；战斗通过普通创建房间、加入、添加三个CPU、Ready、PlayerInput和Rematch接口推进。

验收覆盖：

- 查询首项为表ID1，金币及代币单价均为10；金币购买3份扣30，另一账户代币购买3份扣30。
- 未认证、无角色资料、两种余额不足、无效数量、未知道具和无效请求ID均拒绝，角色资料、库存及快捷栏保持原值。
- 同一请求ID及相同参数重放不重复扣费或增库存；修改数量或币种的冲突请求拒绝。
- 两个账户购买出的实例均通过Kitbag配置到slot4。金币购买的饲料通过普通 `useItem: 5` 在两轮战斗中各使用一次，库存由3减为2、再减为1。
- 三个CPU的普通移动和攻击自然造成损伤；服务端实际回血事件携带skill1、effect0和duration0，两台独立客户端收到相同事件及相同tick的玩家快照。重复输入序号不追加消耗。
- 每台客户端实际收到的通知分别送入现有技能效果与CAS运行时，五个源绘制节点出现后全部有限结束。
- 两轮均通过正常目标或源时间限制结算，第一轮后双方普通Rematch进入第二轮；测试不缩短时间限制，也不注入血量、位置或结算结果。
- PLAYING期间购买拒绝且不扣余额、不改库存。实际停止并重启服务后，余额、剩余库存、slot4和请求重放账本恢复；账户之间保持隔离。库存中的battleQuantity为房间投影，新连接未入战斗时为0，持久拥有数量保留。

## 限制

网络验收证明重建服务的购买、消费、效果通知和持久化链路。CAS验证使用NullEngine及占位纹理验证实际通知驱动的源节点和有限生命周期；浏览器像素、原始游戏服务器购买规则和真实音频输出不在此脚本内验证。
