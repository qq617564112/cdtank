# 外观实例刷新与角色迷彩来源边界（M3-03 / M6-01）

完整原库存/资料刷新回调 `0x43ed18` 使用资料 selector44 的实例 ID 查 `0x43ccf2` 返回记录，只把匹配记录 `+0x1c` 标为装备状态2，不填角色纹理三槽。此实例在原物品表的实际例子是 **10001“救护车顶灯”**，不是 tanktexture 迷彩。真正的战车默认迷彩三列存在于原 tankshop 表；当前已确认其配置内容，账户获得/选择到角色三槽的 producer 尚未确认。

## 一个实际回调链

`0x43ed18` 获取当前资料后，清七组拥有物品 vector，遍历传入消息 `+0x10` 的原 map；对每条记录先清 `+0x1c` 状态，再用真实 `0x43bd09 → 0x4396e0` 按记录 `+0x0c` 的定义 ID 分到对应拥有 vector。实际定义10001走拥有组3、vector `inventory+0x30/+0x34`。原入包 map iterator `0x42de86` 和 vector insertion `0x4387b7` 都在测试中实际执行。

刷新后的 `0x43ee80–0x43eea3` 取得资料 selector44（原 getter `0x42fdc5 → 0x42029e`，字段 `+0x118`），按该实例通过实际 `0x43ccf2` 查拥有记录；存在时仅将记录 `+0x1c` 写为2。未选、选别的实例或查不到时保持已清的状态0。此分支不读取该实例的定义 ID，不查询 tanktexture，不设置 actor 纹理，也不写 `OdlPlayer+0x110`。

四组完整回调用例使用同一原定义10001、实例71、数量1，资料分别选0/71/72/0xFFFFFFFF；结果状态0/2/0/0，记录其他所有字节、定义ID和角色纹理三槽保持原值。拥有 vector 实际插入的是传入原记录指针，后续 `0x43ccf2` 精确返回它。

测试的消息中实例/拥有记录是显式夹具；它只复现客户端收到记录后的刷新，不证明服务器实际发了该记录或账户拥有资格。

## 外观名词与定义引用

原 `item.dat` 的定义10001字段为 `ItemName=救护车顶灯`、`ItemType=5`、`3DType=1`、`Texture3D=10001A`。现存资料 getter 与卸载取证把分类5称为 skin；它在这条实际数据链中消费帽子装饰实例，不能用该名称推断为 U/M/XY 迷彩。

`0x43bd09` 使用的是拥有组分类，10001属于组3；`0x43bd13` 使用物品细分类，这条定义属于5。两者不是同一个分类编号，记录 `+0x0c=10001` 也不是 `tanktexture.recordId=10011/10012/10013`。因此该记录的 `Texture3D` 名称不作为三槽迷彩来源。

## 属性32的实际客户端观察者

完整玩法观察者 `0x42f385` 在非阶段1且角色查找成功时取得原字段 index。它处理5/8/11/12/13/25/27/31/33等分支，属性32走 `0x42f61e → 0x42f986` 的结束路径。测试执行完整入口，字段 getter返回32，确认角色和记录全部字节不变，没有调用皮肤分派 `0x43c8aa`。这个观察者既不产生三槽，也不因属性32自动重设 actor 纹理。

此结论限定已执行的玩法观察者，不将其他记录观察者或创建时外观应用的行为合并推断。

## 原默认迷彩配置

原 `tankshop.dat` 的战车1有明确字段：

| 字段 | tanktexture ID | 原纹理文件名 |
| --- | ---: | --- |
| 默认贴图(炮塔) | 10011 | 001U_001.tga |
| 默认贴图(车身) | 10012 | 001M_001.tga |
| 默认贴图(履带) | 10013 | 001XY_001_A.tga |

这三个原表字段与已经执行的 U/M/XY 组件覆盖合同对应。它们是可用的**默认配置来源**；目前没有执行原购买、赠送或拥有战车初始化如何把配置写入账户资料/角色的路径，所以不会从该表生成生产账户默认值。

`specialtank.dat` 亦有“坦克贴图/坦克贴图_5/坦克贴图_6”三个字段。例如特殊战车10001“呆呆勇士”提供11812/11811/10013。这些字段具有另一个配置来源，未在本回调验证使用及槽位转换。
