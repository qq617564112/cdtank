# NAV导航资源

`recovery/nav.py`完整读取25份NAV v2文件，共1,417,662个栅格单元、41,011个索引三角形。导航数据独立于显示用POL模型，高度和单元有效性已接入服务端移动，索引几何尚未参与路径规划。

## 原加载器依据

原EXE加载器位于VA 0x45760c附近。0x457645读取14字节头，0x45765d引用签名字符串NAV（0x5c6f14）；0x457671接受版本1或2。0x457681取层数，0x457688按头内偏移跳转至栅格数据；0x457733按第二个偏移跳转至索引几何。

版本2每层先读取128字节描述（0x4576ad），再读取两个3f边界向量、两个u32维数（0x4576c2–0x4576ea），按width×height×8读取单元。几何每层读取u16顶点数、u16三角形数；顶点为3f（0x457764），三角形为3u16（0x45777b）。当前全部样本均为版本2、单层，栅格起点14；每层完整数据恰好结束于几何偏移，几何恰好结束于EOF。

## 观测字段

单元保存f32高度和4字节附加字段；解析器以u32保留附加字段。田野路常见值0–7，另有256与11。0x45758f按 `width*z+x` 选取8字节单元；0x4575c5只比较附加字段的第一个字节，返回该字节大于1的布尔值。256的低字节为0，因而无效，不能用整个u32大于1判定。0x457ca0的栅格绘制另读第二个字节，说明附加字段并非单一枚举；其余字节及各数值业务语义仍待还原。

田野路边界约X[-2626.32,1016.72]、Z[-1993.12,1647.31]，栅格303×303。格子宽度、原点及位置换算已由原代码确认，依据如下。版本1没有当前样本，解析器不宣称已支持该版本。

## 验证

`tests/nav-geometry.py`对全部25份源文件核对两个数据偏移、层数、描述、边界、维数、每个高度/附加字段、顶点与索引，并验证文件完整消费及有效顶点索引。摘要保存到 `recovery/output/nav-verification.json`。此检查证明数据布局可读取，不证明原导航行为已实现。

## 原查询代码

- 0x433f92：`ix = trunc((x - minimum.x) * inverse12)`，Z同理，然后调用0x45758f。VA 0x5c4754的f32常量为0.0833333358168602。0x57bb64负责浮点到整数的向零取整。因此原点以下不足12单位的位置仍可能映射到第0格，不能替换成floor。
- 0x44ef9e：验证整数下标处于0到width/height的半开区间。
- 0x45788c：格子中心X/Z为`index * 12 + minimum + 6`，分别使用0x5c6f24的12和0x5e68d0的6。有效格子的Y直接复制单元f32高度；无效格子返回失败，输出Y为0。
- 0x4340c5：位置转下标后读取相应单元。0x434cee构建、旋转和平移多个空间采样点，在0x434f67、0x434f83、0x43502e等位置调用该查询，并根据采样有效性返回不同状态。0x435088调用0x434cee并对部分状态尝试另一组参数。多点形状、各状态及完整移动响应仍需核对。
- 导航接口vtable 0x5c6f28中的0x18/0x1c/0x38槽分别包装位置查询、格子中心查询和单元查询，对应0x45796c/0x45798a/0x45791a。

## 服务端使用

`export_battlefields.py`将全部层的边界、维数及原8字节单元导出；单元以base64保存，完整保留高度和4个附加字节。`apps/server/src/navigation.ts`实现上述坐标换算、低字节有效性及中心查询。当前所有源地图均为单层，Battlefield使用第0层。

移动使用NAV高度，并沿中心轨迹的全部格子边界划分区间，遇到无效单元即停止；端点有效也不能跨越中间无效区域。该连续扫掠是Web服务端的实现策略，原车体多点采样、转向、滑动、台阶和路径算法未宣称等价。原盒体仍参与障碍碰撞，POL三角形仍用于弹丸求交。运行时使用JavaScript双精度及原f32倒数常量，未宣称所有边界处与原x87精度逐位一致。

`tests/battlefield-source.py`核对导出层的边界、维数及每个单元原字节。`npm run test:navigation`逐个验证1,417,662个中心的下标、高度、附加字段和有效性，其中1,074,456个有效；另验证向零取整、越界、低字节与高字节区别、短距离斜穿无效格，以及显示地形存在但NAV无效时服务端阻止移动。
