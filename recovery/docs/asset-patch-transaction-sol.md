# M3-01 更新器替换与失败路径

原CPKUpdate按删除旧条目、保存索引、检查下载、入包的次序替换资源。失败分支没有恢复旧条目的操作；这段原代码不提供原子替换合同。当前32份下载运输内容解码后已与安装归档逐字节相同，不需要为获得最终内容重写原归档。

## 原次序

更新循环`425da7`通过`422956 → 42c010`检查原路径是否存在。存在则`425dd8`调用`422032 → 42bf40`删除包装器。其内部先用路径查索引，再执行完整`422d48 → 42f050`：旧flags加10hex（deleted）、活条目数量减1、deleted数量加1、登记空闲索引、重置父路径/名称块，并递归处理现有孩子。随后`430fa0`写头128字节，`431040`写容量索引。

这一保存完成后，`426035`才检查下载路径：不存在置`ff000040`，进入下一条。存在则`42605d → 42bc00`入包包装器经`42e000 → 42d4b0`执行单文件处理。文件打开失败返回0；`42e25f`触发原`bResult`调试断言，包装器依然写头/索引并返回0。更新循环继续时置`ff000008`并报告失败。没有看到旧索引恢复分支。

直接绕过删除把同CRC活条目再次交给原入包器，`42d55b`重复门禁在读取运输文件之前返回false。包装器会触发相同断言并保存未改变的头/索引；不是按内容相同跳过，也不是自动覆盖。

## 原执行证据

`tests/asset-patch-transaction-sol.py`直接读取现存data.cpk的128字节头和65535容量索引，对32份候选各执行三个样本，共96组：

- 缺下载：完整原删除/索引变更与保存先发生，再检查文件；隔离持久化副本保留deleted位，错误`ff000040`。
- 下载打开失败：原删除后经完整`42bc00/42e000/42d4b0`失败链，持久化副本保留deleted位；调试断言之后继续路径错误`ff000008`。
- 直接live重复：原live CRC二分查找及重复拒绝路径执行，没有打开文件，旧头/索引逐字节不变；包装器仍保存元数据。

保存边界写入隔离bytearray，不修改原归档或原下载。路径标准化/CRC/文件名查索引、CRT字符串、文件存在/打开及seek/write边界供给；原live CRC二分查找、删除主体、头/索引保存包装器、入包包装器/重复门禁/文件打开失败、外层错误次序均执行原指令。记录逐条包含原CPK索引、错误位、保存与文件检查有序调用。

复现：

```bash
recovery/.venv/bin/python tests/asset-patch-transaction-sol.py > recovery/output/asset-patch-transaction-sol.log
```

证据`recovery/output/asset-patch-transaction-sol.json/log`含96个样本及原指令范围。

## 剩余验收

调试断言的UI/终止策略没有仿真；测试以返回继续供给该边界，并保留实际断言调用（`cpkcore.cpp` line1248）。因此错误位记录描述断言继续后的原分支，不宣称原失败时没有弹窗。

成功替换的完整运输读取/解码/压缩、有效载荷写入、索引重排和最终归档再打开尚未在这组原更新器执行测试中完成。已有原解码15个样本与32份最终CPK内容等同性证明了当前最终内容；不能替代完整成功入包验收。M3-01按完整“正确应用”要求保持未勾选，具体剩余为成功入包及上述断言策略，不再列电影/WAV/表格独立来源缺口。
